# 腾讯叮当电子相框项目设计文档

## 1. 项目目标

将一台已刷成电视盒子 Android 系统的腾讯叮当设备，改造成一个长期运行的电子相框终端。

第一版目标是开发一个原生 Android TV 风格 APK，安装到设备后：

- 首次启动时在设备本机输入 Workers 地址、用户名、密码
- 将配置持久化保存到本地
- 开机自动启动
- 自动进入全屏相框模式
- 每 2 小时自动刷新一次图片
- 始终显示服务端判定的“当前最新合格图片”
- 发生异常时显示错误提示页

本项目不是通用相册应用，也不是多媒体管理平台。第一版只解决“单设备、单账户、单张最新图、自动刷新”的核心问题。

## 2. 范围与非目标

### 2.1 第一版范围

客户端能力：

- Android APK，可直接安装到刷机后的腾讯叮当设备
- 本机配置页：输入 `baseUrl`、`username`、`password`
- 本地持久化配置
- 全屏图片展示，按铺满全屏策略显示（允许裁切）
- 开机自启
- 启动即拉取图片
- 每 2 小时自动刷新
- 隐藏设置入口（连续按 5 次 OK 键进入设置页）
- 请求失败 / 鉴权失败 / 无合格图片时显示错误页

服务端能力：

- Cloudflare Workers 接口
- 接收用户名与密码
- 校验访问权限
- 从腾讯云 COS 指定文件夹中选出最新合格图片
- 返回图片 URL 与更新时间

### 2.2 非目标

第一版明确不做：

- 图片轮播
- 多账户切换
- 手机配网页 / 二维码配网
- 云端管理后台
- 本地图库管理
- 图片手势操作、缩放、翻页
- 背景音乐、时钟、天气等附加信息层
- 离线编辑配置
- 高级权限系统

## 3. 用户体验设计

### 3.1 首次使用流程

1. 用户安装 APK
2. 首次打开应用，进入配置页
3. 输入：
   - Workers 地址
   - 用户名
   - 密码
4. 点击保存
5. 应用立即请求服务端
6. 如果成功，进入全屏相框页并显示图片
7. 如果失败，进入错误页并展示原因

### 3.2 日常运行流程

1. 设备开机
2. 应用自动启动
3. 读取本地配置
4. 若配置存在，直接进入相框页并发起刷新
5. 若请求成功，显示最新图片
6. 若请求失败，显示错误页
7. 后台继续按 2 小时间隔重试

### 3.3 设置入口

为了保持“家电感”和低打扰，常态下不显示设置按钮。隐藏入口定义为：

- 在相框页，遥控器连续按 5 次 OK 键
- 进入配置页
- 用户可以修改地址、用户名、密码并重新保存

此方案简单、稳定、低误触，适合电视盒子输入环境。

## 4. 客户端架构设计

### 4.1 页面状态

客户端只保留 3 个核心页面状态：

#### 配置页

用于首次录入或后续修改配置：

- Workers 地址输入框
- 用户名输入框
- 密码输入框
- 保存按钮
- 可选：测试连接提示

要求：

- 适配电视大屏
- 字体较大，焦点清晰
- 支持遥控器方向键操作

#### 相框页

正常展示状态：

- 全屏显示当前图片
- 使用 `centerCrop`/等价策略铺满屏幕
- 不显示顶部栏、底部栏、时间或其他 UI 干扰

#### 错误页

异常展示状态：

- 显示简短错误文案
- 不展示复杂调试信息
- 可提示后台会自动重试

建议错误类型映射：

- `AUTH_FAILED` → 用户名或密码错误
- `NO_IMAGE` → 暂无符合条件的图片
- `REQUEST_FAILED` → 网络请求失败
- `INVALID_RESPONSE` → 服务返回异常

### 4.2 本地存储

建议本地持久化以下数据：

- `baseUrl`
- `username`
- `password`
- `lastImageUrl`
- `lastUpdatedAt`
- `lastErrorCode`（可选）

这些数据足以支持重启恢复、重复刷新和错误恢复。

### 4.3 刷新调度

刷新机制：

- 应用启动后立即刷新一次
- 之后每 2 小时刷新一次
- 如果设备休眠/唤醒，恢复时应尽快补一次刷新检查

调度目标：

- 实现简单可靠
- 不追求秒级实时
- 优先保证长期稳定运行

### 4.4 图片加载策略

客户端每次请求服务端拿到 `imageUrl` 后：

1. 下载图片
2. 校验下载成功
3. 替换当前画面
4. 记录本次成功的 URL 和更新时间

如果下载失败：

- 切到错误页
- 不保留“看似成功但实际已失效”的状态

第一版不强制要求复杂缓存淘汰策略，但应至少支持“当前图片可稳定展示”。

### 4.5 开机自启

应用需监听 Android 开机启动相关广播，在设备开机后自动启动主流程：

- 读取本地配置
- 若未配置则进入配置页
- 若已配置则进入相框页并执行刷新

这是第一版核心体验之一，不可省略。

## 5. 服务端架构设计

### 5.1 服务职责

Cloudflare Workers 负责：

- 接收客户端请求
- 校验用户名和密码
- 定位 COS 文件夹
- 找出最新合格图片
- 返回图片 URL

客户端不承担图片筛选逻辑，只承担配置、调度和展示逻辑。

### 5.2 接口设计

建议第一版固定为单接口：

### `POST /frame`

请求体：

```json
{
  "username": "example-user",
  "password": "example-pass"
}
```

成功响应：

```json
{
  "ok": true,
  "imageUrl": "https://example.com/path/to/image.jpg",
  "updatedAt": "2026-04-28T10:00:00Z"
}
```

失败响应：

```json
{
  "ok": false,
  "code": "NO_IMAGE",
  "message": "No eligible image found"
}
```

### 5.3 鉴权逻辑

已确认的业务规则：

- 用户名对应腾讯云 COS 上的文件夹名
- 密码对应一个“密码文件名”概念
- 只有存在该密码校验文件时，才允许访问对应文件夹图片

第一版设计上，Workers 应将客户端传入的用户名和密码映射为：

- `username` → COS 中目标文件夹
- `password` → 与该文件夹配套的密码校验文件标识

如果密码文件不存在，则返回 `AUTH_FAILED`。

### 5.4 选图逻辑

Workers 需要从目标文件夹中按“从新到旧”的顺序寻找图片，并应用以下筛选条件：

- 必须是图片文件
- 分辨率必须 **宽 > 1280 且高 > 800**
- 取满足条件的第一张，即“最新合格图片”

如果最新文件不合格，则继续向前查找，直到找到符合条件的图片。

如果最终没有任何合格图片，则返回 `NO_IMAGE`。

### 5.5 图片返回方式

第一版已确认：

- Workers 返回图片 URL
- 不直接返回图片二进制流

这样做的原因：

- 客户端实现更简单
- 服务端压力更小
- 后续如需切换为签名 URL 或代理 URL，也不影响客户端主流程

## 6. 数据流设计

标准成功链路：

1. 设备开机
2. APK 自动启动
3. 读取本地配置
4. 调用 `POST /frame`
5. Workers 校验用户名/密码
6. Workers 在 COS 中查找最新合格图片
7. Workers 返回 `imageUrl`
8. 客户端下载并全屏展示
9. 2 小时后再次执行相同流程

失败链路：

1. 客户端调用 `POST /frame`
2. 服务端返回错误，或客户端请求/下载失败
3. 客户端进入错误页
4. 后台保持定时重试
5. 一旦后续成功，再切回相框页

## 7. 错误处理策略

第一版错误处理目标：

- 用户能明确知道当前没有正常显示的原因
- 系统无需用户干预即可继续重试
- 错误状态简单明确，不做复杂恢复 UI

建议错误页文案风格：

- 网络请求失败，请稍后自动重试
- 用户名或密码错误
- 暂无符合条件的图片
- 服务响应异常，请稍后自动重试

错误页应保留隐藏设置入口，便于修改错误配置。

## 8. 技术取舍与设计决策

### 8.1 为什么选原生 Android APK

原因：

- 最适合电视盒子设备形态
- 更容易做开机自启、焦点导航、沉浸式全屏
- 长期稳定性优于 WebView 壳方案
- 更像“家电式终端”而不是“打开网页”

### 8.2 为什么客户端尽量简单

业务判断集中在 Workers 侧，客户端只负责：

- 配置
- 定时请求
- 下载图片
- 全屏显示
- 错误展示

这样有利于：

- 降低 APK 复杂度
- 后续服务端调整选图逻辑时不必频繁发版
- 将账号目录与图片筛选规则统一收口在服务端

### 8.3 为什么第一版不做轮播

“电子相框”这个项目的第一版核心不是做相册浏览器，而是做一个长期稳定展示“最新指定图片”的终端。轮播、多图策略和播放顺序会显著增加状态复杂度，因此第一版明确排除。

## 9. 验收标准

第一版完成后，应满足以下验收条件：

1. APK 可以安装到目标设备
2. 首次启动可输入并保存地址、用户名、密码
3. 重启设备后无需重新输入配置
4. 设备开机后应用可以自动启动
5. 应用可自动请求 Workers 接口
6. 接口成功时，全屏显示返回的图片 URL 对应图片
7. 图片按铺满全屏策略展示
8. 每 2 小时自动刷新一次
9. 鉴权失败 / 请求失败 / 无合格图片时显示对应错误页
10. 用户可通过隐藏入口重新进入设置页

## 10. 风险与后续事项

### 10.1 已知风险

- 电视盒子系统的自启动权限策略可能因 ROM 而异，需要实机验证
- 腾讯云 COS 文件列表与图片尺寸获取方式，可能影响 Workers 实现复杂度
- 如果 COS 原始图片地址不可直接公开访问，后续可能需要签名 URL 或 Workers 代理下载
- 遥控器输入体验较弱，因此配置页必须尽量简化

### 10.2 后续可扩展方向

不纳入第一版，但可作为后续迭代：

- 多图轮播
- 自定义刷新间隔
- 显示最近更新时间
- 更隐蔽或更友好的设置入口
- 图片预缓存
- 设备端日志导出
- 后台管理与账户配置工具

## 11. 实施建议

建议将项目拆成两个独立交付面：

1. **Android 客户端项目**
   - 负责配置、展示、自启、刷新、错误页
2. **Cloudflare Workers 项目**
   - 负责鉴权、查图、返回图片 URL

这样可以分别开发、联调与部署，也更符合后续维护方式。
